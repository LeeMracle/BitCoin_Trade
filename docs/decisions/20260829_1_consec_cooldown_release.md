# ADR 20260829-1 — 5연패 쿨다운을 실제로 해제한다

- **일자**: 2026-08-29
- **상태**: 채택 (사용자 승인)
- **관련**: lessons #38(floor 메커니즘), #30(알람 디바운스), #46(수동 개입 분리)

## 배경 — 72시간이 72시간이 아니었다

2026-08-28 하락장에서 5종목이 연속 손절돼 브레이커가 발동했다(정상 동작).
그런데 쿨다운 만료 후 무엇이 벌어지는지 확인하니:

```
08-31 16:15 UTC  쿨다운 만료 → 매수 재개 (약 7시간 45분)
09-01 00:00 UTC  _refresh_levels() 일일 실행
                 → check_consec_loss() 가 closed_trades 재계산
                 → 5연패 그대로 (매수가 막혀 새 청산이 없었으므로)
                 → cooldown = now + 72h 재설정
09-04 00:00 UTC  또 만료 → 또 재설정 …
```

**안전장치의 해제 조건이 그 장치 자신이 만든 상태에 의존한다.**
매수를 막아서 연패를 못 깨고, 연패가 안 깨져서 매수를 막는다. 자기충족적 잠금이다.
`72h` 라는 이름이 실제로는 **"이길 때까지 무기한"** 이었다.

유일한 자동 탈출은 **보유 포지션이 이익으로 청산**되는 것인데, 08-29 시점 보유 3종목의
자금가중 수익률은 EGLD -3.73% / VTHO -2.63% / BLAST +2.44% 로 하나뿐이었고
그마저 트레일링스탑까지 밀리면 손실로 뒤집힌다. **전부 손절되면 8연패가 되어
현금 100%로 영구 동결**된다.

## 결정

쿨다운을 **복역 완료**하면 `consec_loss_floor_date` 를 현재 시각으로 밀어
해당 연패를 산정에서 제외한다. 즉 72h 가 실제로 72h 가 되게 한다.

`cooldown_until` 만 0 으로 만드는 방식은 쓰지 않는다 — lessons #38 이 기록한 대로
다음 재계산에서 그대로 부활한다.

## 핵심 설계 — 부과와 해제를 어떻게 구분하는가

만료 시점에 `consec >= 5` 인 상태는 **두 가지가 섞여 있다**:

| | 상황 | 해야 할 일 |
| --- | --- | --- |
| (a) | 이 연패로 처음 걸림 | 72h **부과** |
| (b) | 이 연패로 이미 72h 복역 | **해제** |

`cooldown_until` 이 과거값이라는 것만으로 구분하면 **과거에 한 번이라도 쿨다운이
있었던 계좌는 새 5연패도 즉시 해제**되어 안전장치가 통째로 무력화된다.

→ 부과 시 **어떤 연패에 대한 것인지 지문**(`cooldown_imposed_for` = 스트릭 마지막
손실의 `exit_date`)을 기록하고, 만료 시 현재 스트릭의 지문과 대조한다.
같으면 복역 완료(해제), 다르면 그 사이 새 손실이 생긴 것(재부과).

지문 산정(`_consec_streak_tail`)은 연패 산정과 **동일한 규칙**(floor +
`counts_for_consec_loss`)을 써야 한다. 한쪽만 적용하면 지문이 어긋나 해제가
영영 성립하지 않는다(lessons #38 경로 A/B 불일치 계열).

## 보존되는 것

- **누적 통계**: `n`/`wins` 는 `strategy_start` 기준이라 floor 이동과 무관.
  검증 표본(ADR 20260823-1)은 그대로 유지된다.
- **수동 개입 분리**(lessons #46): 지문·연패 산정 모두 `counts_for_consec_loss` 적용.
- **알람 디바운스**(lessons #30): 해제 알림도 1회만.

## 반복 감시

`consec_loss_release_count` 를 증가시키고 알림에 **"N회째 해제"** 를 명시한다.
반복된다는 것은 전략이 실제로 망가졌다는 신호이므로 숫자가 보여야 한다.
자동 에스컬레이션(2회째부터 더 길게 등)은 **넣지 않았다** — 근거가 될 데이터가 없다.

## 대안과 기각 사유

| 대안 | 기각 사유 |
| --- | --- |
| 만료 시 `cooldown_until = 0` 만 | 다음 재계산에서 부활 (lessons #38 함정 그대로) |
| 지문 없이 "만료면 무조건 해제" | 과거 쿨다운 이력이 새 연패를 무력화 |
| 수동 해제만 유지(현행) | 사람이 개입 못 하면 영구 동결. "72h" 라는 이름과 불일치 |
| 해제 시 에스컬레이션(144h 등) | 근거 데이터 없음. 임의 상수 추가는 나중에 검증 불가 |

## 검증

- 시나리오 시뮬레이션 4/4 (부과→만료→해제 / 과거이력+새연패 / 쿨다운중 새손실 / 승리로 자연해소)
- `pre_deploy_check.check_consec_cooldown_releases()` 역방향 10/10
  - ⚠ 초안 룰이 `src.count(...) >= 3` 개수 검사였는데 **기록만 지워도 통과**했다.
    지문은 기록·대조·삭제 세 동작이 모두 있어야 성립하므로 **각각의 문법 형태**로
    따로 검사하도록 수정. 개수 세기는 "이름이 존재하는가"의 변형이다(동일 유형 8회째).

## 즉시 효과

현재 걸려 있는 쿨다운(08-31 16:15 UTC 만료)은 `cooldown_imposed_for` 가 없으므로
만료 시 (a) 로 판정되어 **한 번 더 72h 가 부과된다**. 그 다음 만료(09-03경)부터
정상 해제된다. 지금 즉시 풀려면 별도 조치가 필요하며, 08-29 시점 시장이
하락 중이라 권하지 않는다.
