# ADR 20260823-1 — 검증 기준선 재설정 및 판정 기준 전환

- **작성일(KST)**: 2026-08-23 08:30
- **상태**: 적용 완료
- **관련**: [lessons #40](../lessons/20260822_1_vol_filter_stale_snapshot.md), [#41](../lessons/20260822_2_trail_stop_not_persisted.md), [#42](../lessons/20260822_3_positions_unsubscribed.md), [#43](../lessons/20260822_4_exec_price_not_settled.md)

## 배경

봇이 스스로 내던 판정은 다음과 같았다.

```
검증 146일차 — 거래 16건 (백테스트 목표: 승률 35%+, 평균 +0.5%+)
실제: 승률 19% | 평균 -6.3%
🏁 7일 최종판정: FAIL
```

이 판정을 그대로 받아들이면 전략을 폐기하는 결론에 이른다.
그러나 **이 숫자는 세 가지 이유로 전략의 성적이 아니다.**

### (1) 실행 버그 4건이 매매를 오염시켰다

2026-08-22에 발견·수정한 것들이다.

| # | 버그 | 매매에 미친 영향 |
|---|---|---|
| #40 | 거래량 필터가 미완성 봉을 24h 캐시 | **매수 신호 100% 차단** (하루 70,388건) |
| #41 | 트레일스탑 고점 갱신 미저장 | 재시작 시 이익 보호 소멸 |
| #42 | 매수 직후 보유종목이 웹소켓 구독에서 탈락 | **손절·트레일·익절이 아예 미평가** |
| #43 | 체결가 대신 신호가 기록 | `exit_price`·`return_pct`·`closed_trades` 전부 오염 |

특히 #43은 성과 통계 자체를 직접 오염시킨다. **"승률 19%"는 부정확한
체결가 위에서 계산된 값**이다.

### (2) 그 기간 전략 파라미터가 반복 변경됐다

`strategy_start = 2026-03-29` 창 안에서:

- DC 기간: 50 → 20 → 15 → 10 → 15 → 12
- MIN_VOLUME_KRW: 5억 → 3억 → 5억
- 레짐 필터: OFF → ON
- VOL 필터 배수: 1.0 → 1.5
- MAX_ATR_PCT: 0.10 → 0.07

**서로 다른 전략의 성적을 하나로 합산**하고 있었다. 어떤 파라미터가 좋았는지
나빴는지 이 통계로는 구분할 수 없다.

### (3) 거래가 "허용"된 날이 거의 없었다

레짐 게이트(BTC > EMA200) 통과율:

| 분기 | 통과일 | 비율 |
|---|---|---|
| 2025Q3 | 92/92 | 100.0% |
| 2025Q4 | 37/92 | 40.2% |
| 2026Q1 | 0/90 | **0.0%** |
| 2026Q2 | 0/91 | **0.0%** |
| 2026Q3 | 2/53 | 3.8% |

최근 180일 통과율 **1.1%**. 2026년 내내 전략은 거래할 수 없는 상태였고,
2026-08-22에 처음 게이트가 열렸다.

즉 "146일차"라는 표현은 그 146일 중 거래 가능일이 거의 없었다는 사실을 감춘다.
그리고 **달력 기반 판정("7일 지났으니 최종판정")은 표본 0건에도 결론을 낸다.**

## 결정

### 1. 검증 창을 2026-08-23으로 이동

```
strategy_start          2026-03-29      → 2026-08-23
consec_loss_floor_date  2026-06-06 00:05 → 2026-08-23
regime_open_days        (신설)           → 0
```

절단점을 08-23으로 잡은 이유: 마지막 매매 로직 수정(#43 체결가 확정)이
2026-08-22 06:47 UTC 배포였고, 그 이후 청산된 거래가 없다.
08-22로 잡으면 버그 시절 XRP/SUI(-10% 2건)가 새 창에 섞인다.

**`closed_trades` 26건은 삭제하지 않는다.** 창 밖으로 밀려날 뿐 이력은 보존된다
(창 밖 18건: 승률 17%, 평균 -6.68%).

### 2. 목표치를 현재 config 실측에서 재도출

기존 `승률 35%+ / 평균 +0.5%+`는 TP(+5%/+12%) 도입 **이전** 설정의 잔재로 추정된다.
TP1이 +5%에서 절반을 실현하는 현재 구조는 승률이 구조적으로 높고 평균수익은 낮다.

현재 config 백테스트 (`scripts/calibrate_strategy_baseline.py`,
506건 / 54종목 / 700일, 수수료 0.05%×2 반영):

```
승률 59.9% | 평균 +1.50% | PF 1.51 | 평균보유 5.6일 | 최대손실 -10.09%
```

목표치는 **기대의 하한**으로 잡는다 — 기대치를 그대로 목표로 삼으면
구조적으로 절반이 FAIL이 된다.

```
_BACKTEST_TARGET_WINRATE  35 → 48   (기대 59.9%의 80%)
_BACKTEST_TARGET_AVG_RET  0.5 → 0.75 (기대 +1.50%의 50%)
```

### 3. 판정을 달력 기반 → 표본 수 기반으로 전환

```python
# 변경 전
if days_elapsed >= 7 and n >= 15:   # 시간이 조건에 들어감
# 변경 후
if n >= _VERDICT_MIN_TRADES:        # 표본 수만 본다 (30건)
elif n >= _INTERIM_MIN_TRADES:      # 중간점검 (15건)
```

최소 표본을 15 → **30건**으로 상향했다. 승률 60% 가설과 35% 가설을 구분하려면
15건으로는 신뢰구간이 너무 넓다.

또한 PASS 조건에 평균수익 기준을 추가했다 — 기존에는 승률만 봤다.

### 4. 거래 가능일(regime_open_days) 계측 신설

레짐 게이트가 열려 있던 날만 센다. 성과 요약에 함께 표시한다.

```
검증 N일차 (거래가능 M일) — 거래 X건
```

달력 일수만 보면 검증 진척에 착시가 생긴다 — 위 (3)의 근본 원인이다.

## 재검증 소요 예상

측정된 신호 빈도(0.75건/일)와 슬롯 처리량(5슬롯 / 평균보유 5.6일 = 0.90건/일)
기준, **레짐이 열려 있다는 전제 하에**:

| 표본 | 소요 |
|---|---|
| 15건 (중간점검) | 약 20일 |
| 30건 (최종판정) | 약 40일 |
| 50건 | 약 66일 |

**단, 이는 레짐이 계속 열려 있을 때의 이야기다.** 최근 180일 통과율이 1.1%였음을
감안하면 달력 시간은 이보다 훨씬 길어질 수 있다. 그래서 판정을 시간이 아닌
표본 수 기준으로 바꾼 것이다.

## 알려진 한계 (판정 시 감안할 것)

**현재 보유 5종목(JUP/SPK/TAIKO/OP/POL)은 기준일 이전에 진입했다.**
진입가는 `fix_entry_price_from_fills.py`로 실체결가 보정을 마쳤으나,
진입 *선택* 자체는 버그 시절 필터(특히 #40 거래량 필터가 사실상 무작위로
동작하던 구간)를 통과한 것이다. 새 창의 첫 5건은 이 오염을 안고 있다.

## 검증규칙

`pre_deploy_check.check_validation_baseline()` 신설:

1. `_DEFAULT_STRATEGY_START`가 2026-08-23 이전으로 회귀하지 않았는지
2. 목표치가 옛 값(35% / 0.5%) 수준으로 회귀하지 않았는지
3. 판정이 표본 수 기준인지 (`days_elapsed >= N and n >= M` 형태 금지)
4. 성과 요약에 거래가능일이 표시되는지 (warning)
5. 연패 산정 경로가 기준일 기본값을 자체정의하지 않는지 (교훈 #19)

역방향 검증: 5개 회귀 시나리오 전부 발화 확인, 정상 코드 0건.

## 교훈

1. **"몇 일차"는 검증 진척의 지표가 아니다.** 전략이 거래할 수 없는 날은
   아무리 흘러도 정보가 쌓이지 않는다. 게이트가 있는 시스템은
   **게이트가 열린 시간**을 세야 한다.
2. **목표치도 설정의 일부다.** 전략 파라미터를 바꾸면서 판정 기준을 그대로 두면,
   판정이 조용히 무의미해진다. TP를 도입한 순간 승률의 의미가 바뀌었는데
   목표는 그대로였다.
3. **기준선을 옮길 때는 이력을 지우지 말고 창만 옮긴다.** `closed_trades`를
   삭제했다면 나중에 "그때 실제로 뭐가 일어났는지" 확인할 방법이 사라진다.
