# 매수 직후 보유 종목이 웹소켓 구독에서 탈락 — 손절·익절 무방비

- **카테고리**: 안전장치 / 자료구조 이중 용도

## 원인

`_execute_buy()` — 재매수 방지를 위해 레벨에서 삭제:

```python
# 돌파 후 동일 종목 재매수 방지 (레벨에서 제거)
if symbol in self.levels:
    del self.levels[symbol]
```

웹소켓 구독 목록 — **바로 그 `self.levels`에서 생성**:

```python
upbit_codes = []
for sym in self.levels.keys():
    coin = sym.split("/")[0]
    upbit_codes.append(f"KRW-{coin}")
```

웹소켓은 약 10분마다 재연결하고 그때마다 구독을 재구성한다.
따라서 **매수 후 첫 재연결부터 보유 종목의 틱이 끊긴다.**

`_on_ticker()`는 틱이 와야 실행되고, 그 안에 다음이 전부 들어 있다:

- 고점 갱신 및 트레일링스탑 상향
- **트레일링스탑 이탈 매도** (`if price < pos["trail_stop"]`)
- **하드 손절 캡**
- **부분 익절** (`_check_tp_levels`)

즉 매수 직후부터 다음 날 00:00 레벨 갱신 때까지 **포지션이 무방비 상태**였다.
하락했다면 손절도 실행되지 않았을 것이다 — 이번엔 상승장이라 익절 지연으로만 드러났다.

### 근본 원인

**`self.levels`가 두 가지 용도로 쓰인다.**

1. "매수 후보 목록" — 매수하면 제거하는 것이 맞다
2. "구독 대상 목록" — 보유 종목은 오히려 **반드시** 포함해야 한다

두 의미가 한 자료구조에 얹혀 있어, 1번 관점의 정당한 삭제가 2번을 조용히 파괴했다.

실제로 같은 구독 구성부에는 예외 처리가 이미 두 개 있었다:

```python
# vol_reversal DRY-RUN 보유종목도 구독에 추가   ← 있음
# EMA Trend Follow: BTC/KRW 반드시 구독 포함     ← 있음
```

**보조 전략의 포지션과 BTC는 챙기면서, 메인 전략 자기 포지션만 빠져 있었다.**

## 수정

```python
# 메인 전략 보유종목 반드시 구독 포함
for sym in self.state.get("positions", {}).keys():
    code = f"KRW-{sym.split('/')[0]}"
    if code not in upbit_codes:
        upbit_codes.append(code)
```

`self.levels`(매수 후보)와 구독 대상을 분리. 재매수 방지 로직은 그대로 둔다
— 보유 중이면 `_on_ticker`가 `if symbol in positions:` 분기로 빠져
매수 경로에 도달하지 않으므로 중복 매수 위험은 없다.

## 교훈

1. **한 자료구조를 두 의미로 쓰면, 한쪽 관점의 올바른 변경이 다른 쪽을 조용히 부순다.**
   `self.levels`에서 매수 종목을 지우는 것은 "후보 목록" 관점에선 100% 옳다.
   그 목록이 동시에 "구독 대상"이라는 사실이 코드 어디에도 표시돼 있지 않았다.
2. **예외 목록에 항목이 쌓이면 그 자체가 설계 결함 신호다.** VR 포지션·BTC를
   따로 챙기는 코드가 이미 있었다 = "levels만으론 부족하다"를 두 번 인정한 것.
   그때 구독 대상을 별도로 산출했다면 이 사고는 없었다.
3. **안전장치는 "실행됐는가"가 아니라 "평가될 기회가 있었는가"까지 확인해야 한다.**
   손절 코드는 완벽했지만 입력(틱)이 오지 않았다. 로그에 오류 한 줄 없었고
   알람도 울리지 않았다 — 전형적 silent fail (교훈 #31 계열).
4. **상승장이 버그를 가린다.** 하락했다면 손절 미발동으로 큰 손실이 났을 사고가,
   상승 중이라 "익절이 좀 늦네" 수준으로만 보였다.
