# 거래량 필터가 "방금 열린 봉"을 24시간 캐시 — 전 종목 매수 100% 차단

- **발생일**: 2026-08-22 (감지), 도입 2026-05-04 (plan 20260504_2 AC7)
- **심각도**: CRITICAL (매수 경로 전면 차단, 유휴 현금 111,017 KRW)
- **카테고리**: 전략 필터 / 봉 기준 혼동 / silent fail

## 증상

BTC가 EMA(200)를 상향 돌파해 레짐 게이트가 열린 첫날(2026-08-22),
현금 111,017 KRW를 보유했음에도 00:05 UTC 이후 매수가 **1건도 발생하지 않음**.

`workspace/filter_stats.json`:

```json
{ "date": "2026-08-22", "counters": { "ema200_filter": 1, "unknown_vol_filter": 70388 } }
```

로그:

```
[DOGE/KRW] 거래량 필터 — 6356 < 213003006×1.5 차단
[XRP/KRW]  거래량 필터 — 104938 < 152714672×1.5 차단
```

현재 거래량이 5일 평균의 **1/33,000** 수준 — 정상 시장에서 나올 수 없는 값.

## 원인

`services/execution/realtime_monitor.py::refresh_levels()`

```python
refresh_key = now.strftime("%Y-%m-%d")     # UTC 날짜 → 하루 1회만 갱신
...
vol_sma    = float(pd.Series(df["volume"]).rolling(5).mean().iloc[-1])
latest_vol = float(df["volume"].iloc[-1])  # ← 방금 열린 오늘 일봉
```

1. `refresh_levels()`는 **UTC 00:00 직후 하루 1회**만 실행된다.
2. 그 시점의 `df["volume"].iloc[-1]`은 **개장 수십 초~수 분 된 오늘 일봉**의 누적 거래량 — 거의 0.
3. 이 값이 `self.levels`에 저장되어 **24시간 동안 고정 재사용**된다.
4. 따라서 `latest_vol < vol_sma * 1.5`가 전 종목·하루 종일 참 → 매수 신호 100% 차단.

### 재현 증거

동일 코드를 04:39 UTC에 실행한 결과:

| 심볼 | 00:00 캐시된 `latest_vol` | 04:39 실제 `latest_vol` |
|---|---:|---:|
| DOGE | 6,356 | 205,607,203 |

같은 일봉인데 4시간 반 만에 거래량이 3만 배 누적 — 캐시된 값이 무의미한 스냅샷임을 확정.

### 왜 3건은 통과했나

레벨 갱신 루프는 00:00:14~00:03:52 동안 214종목을 순회한다. 뒤늦게 조회된 종목은
2~3분치 거래량이 쌓여 있었고, 마침 그 순간 거래량이 폭발한 3종목(JUP/SPK/TAIKO)만
1.5배를 넘겼다. 즉 필터가 **"자정 직후 몇 분간 거래량이 터진 종목"** 이라는
사실상 무작위 조건으로 변질된 상태였다.

### 근본 원인

**백테스트와 실시간의 "봉 기준" 불일치.**
백테스트(`services/strategies/advanced.py:348`)는 봉이 **마감된** 시점에
`volume[i] > vol_sma[i] * mult`를 평가한다. 실시간 봇은 봉이 **열린 직후** 값을 읽어
하루 종일 재사용한다. 같은 수식이 백테스트에선 "오늘 거래량이 터졌나?",
실시간에선 "자정 0시 30초 동안 거래량이 터졌나?"로 의미가 뒤바뀌었다.

교훈 #1(틱 vs 봉 진입)의 변종 — 그때는 *진입 시점*, 이번은 *필터 입력값*.

## 수정 (A안 — 완성봉 기준)

`realtime_monitor.py::refresh_levels()`

```python
# iloc[-2] = 직전 "완성된" 일봉. iloc[-1]은 금지.
if len(df) >= 7:                                # -2 + rolling(5) → 최소 7봉
    vol_sma    = float(pd.Series(df["volume"]).rolling(5).mean().iloc[-2])
    latest_vol = float(df["volume"].iloc[-2])
```

- `vol_sma`/`latest_vol` **양쪽 모두** `-2`로 이동해야 백테스트 수식과 일치한다
  (`vol_sma[i]`는 i를 포함한 5봉 평균이므로 한쪽만 옮기면 기준이 어긋남).
- 최소 봉 수 가드도 `6 → 7`. 부족하면 `vol_sma`가 NaN→0이 되어
  `if vol_sma > 0` 가드에서 **필터가 통째로 무력화**된다 (반대 방향 사고).

## 남은 한계 (A안의 알려진 트레이드오프)

값이 00:00 UTC에 1회 계산되어 하루 캐시되므로, 이 게이트의 의미는
**"어제 거래량이 터졌나"** 라는 시장 전반·일 단위 조건이다.
"지금 이 돌파에 거래량이 실렸나"라는 신호별 확인은 아니다.

→ B안(돌파 시점 현재 봉 거래량 실시간 조회 + 경과시간 비례 환산)은
   백테스트 의도에 더 가깝지만 종목별 API 호출 증가(Rate Limit 29 req/s)와
   환산 계수 튜닝이 필요하다. 백테스트로 효과 검증 후 별도 ADR로 전환 검토.

## 검증규칙 (pre_deploy_check.py)

`check_vol_filter_completed_bar()` 신설:

1. composite 분기의 `vol_sma`/`latest_vol`이 **둘 다 `iloc[-2]`** 사용
2. 최소 봉 수 가드가 **7 이상**
3. 패턴 자체를 못 찾으면 **ERROR** (조용히 통과하는 사문화 룰 방지)

버그 재현본에 대해 1·2번 모두 발화하는 것을 확인함 (역방향 검증 통과).

## 교훈

1. **"진행 중인 봉"과 "완성된 봉"을 코드에서 명시적으로 구분하라.** `iloc[-1]`은
   실시간 경로에서 항상 미완성 봉이다. 갱신 주기가 봉 주기와 같으면 값은 항상 ≈0이 된다.
2. **캐시 수명 > 데이터 수명이면 조용히 썩는다.** 하루 1회 갱신되는 캐시에
   분 단위로 변하는 값을 넣으면 안 된다. 캐시에 넣는 값은 그 캐시 주기 동안
   유효해야 한다 — 완성봉 값은 유효하고, 진행 중 봉 값은 아니다.
3. **필터의 조용한 실패는 "신호 없음"으로 위장된다.** 손실이 안 나니 알람도 안 울린다.
   차단 사유별 카운터(`filter_stats.json`)가 없었으면 발견이 훨씬 늦었을 것이다.
   **차단도 관측 대상이다** — 통과율 0%가 며칠 지속되면 경보를 울려야 한다.
