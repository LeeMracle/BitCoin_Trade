# 교훈 #50 — 판단 트리거인 숫자를 문서에 손으로 적으면 재현 불가가 된다

- **일자**: 2026-09-09
- **사고 유형**: 계측 무결성 (틀린 값이 아니라 **검증 불가능한 값**)
- **관련**: [research/20260825_2](../../workspace/research/20260825_2_ml_gate_assessment.md),
  lessons #19(자체정의 금지), #7(1일 1회 작업은 상태 저장 필수 — 재발), #44(역방향 테스트)

## 무슨 일이 있었나

ROADMAP 에 이렇게 적혀 있었다.

```
| ML 게이트 LIVE 전환 | 대기 | shadow 독립표본 186 / 800 |
```

이 186 을 재현하려 했으나 **어떤 정의로도 나오지 않았다.** 실측은 **46** 이다.

186 이 불가능하다는 증명은 짧다 — 이 계수는 **단조증가**한다. 09-07 에 186 이었다면
09-09 에는 186 이상이어야 한다. 그런데 어떤 창으로 세도 46~133 이다.
즉 계산이 갈라진 게 아니라 **애초에 산출된 적이 없는 숫자**였다.

### 왜 위험한가

이 숫자는 ML 게이트를 LIVE 로 켜는(= 매수 차단을 재개하는) **유일한 트리거**다.
실제보다 크게 세면 준비되지 않은 게이트가 켜진다. 그 결과는 이미 겪었다 —
2026-05 LIVE 기간 차단률 100%, 통과 매수 4건 중 3건 손실, 슬롯이 놀았다.

## 원인

로그를 실측하니 계수 기준이 **네 갈래**로 갈릴 수 있었고, 어느 것을 쓸지가
문서에도 코드에도 없었다.

| 갈림길 | 세면 | 안 세면 |
|---|---|---|
| `kind:"outcome"` 결과 라벨행 | 4,505 | 2,885 |
| `ml_active:false` 자리표시자(`score=1.0`) | 2,885 | 2,870 |
| 2026-08-25 중복억제 배포 이전 | 2,870 | 58 |
| outcome 라벨이 아직 없는 신호 | 58 | 51 |
| (종목,종류,날짜) 중복 | 51 | **46** |

같은 로그가 정의에 따라 **4,505 에서 46 까지 98배** 달라진다.
"독립표본"이라는 말이 이 다섯 결정을 하나도 지정하지 않았던 것이 원인이다.

## 수정

정의를 **집행 가능한 술어**로 고정하고, 사람이 아니라 스크립트가 답하게 했다.

- `services/ml/config.py` — `SHADOW_SAMPLE_START` / `SHADOW_SAMPLE_TARGET` /
  `SHADOW_DEDUP_KEY` 단일 출처 (lessons #19)
- `scripts/ml_shadow_count.py` — 이 정의의 **유일한 구현**. 숫자뿐 아니라
  산출 과정(무엇을 몇 건 버렸는지)을 같이 출력한다
- ROADMAP 은 숫자 옆에 산출 명령을 함께 적는다

표본 자격 = 아래 4개를 모두 만족한 뒤 (종목,종류,UTC날짜) 중복 제거:
1. 신호행일 것 (`kind` 없음) 2. 실제 추론일 것 (`ml_active is True`)
3. 기준일 이후일 것 4. **outcome 라벨이 붙었을 것**

4번이 특히 중요하다. 800 은 "도달률이 오르는지"의 검정력에서 나온 수이고,
도달률의 분모는 **결과를 아는 신호**뿐이다. 미라벨 신호를 세는 건 분모 부풀리기다.

## 부수 발견 — 중복 억제가 재시작을 못 견딘다 (lessons #7 재발)

`services/ml/shadow.py` 의 억제 키가 **프로세스 메모리**다.

```python
_seen_keys: set[tuple[str, str, str]] = set()   # 재시작하면 사라진다
```

그래서 "신호 1건 = 기록 1건"이라는 전제가 재시작일에 깨진다 — 실측 5쌍이
그렇게 생겼고, 그중 3쌍(ORCA·DOT·IOST)은 **09-07 13:21 UTC 봇 재시작 시각**과 일치한다.
lessons #7("1일 1회 작업은 날짜 체크 + **상태 저장** 필수 — 재시작 시 중복 실행 방지")이
ML 로거에서 그대로 재발한 것이다.

🔴 **이번에 고치지 않았다.** Phase 3 실거래 표본 누적 중(19/50)이라 라이브 코드 변경은
봇 재시작을 부른다. 계수 정확성은 **읽기 시점 중복 제거**로 전량 해결되므로 라이브를
건드릴 이유가 없었다. 수정은 판정 세션 이후 별건으로 남긴다.

## 검증규칙 (pre_deploy_check)

`check_ml_shadow_count_basis()`:
1. 계수 상수가 `services/ml/config.py` 에 있는가 (AST)
2. 계수 스크립트가 그걸 **import** 하는가 / 자체 정의하지 않는가 (AST — 배치 질문, #45·#49)
3. 표본 자격 4개 술어가 모두 구현돼 있는가
4. ROADMAP 이 숫자를 적을 때 산출 스크립트를 인용하는가

역방향 테스트 **5/5 검출 · 무위반 오탐 없음**.

## 교훈

**판단의 트리거가 되는 숫자는 문서에 적는 순간 검증 대상에서 빠진다.**
코드는 pre_deploy_check 가 지키고 파라미터는 config 가 지키는데, 문서의 숫자는
아무도 지키지 않는다. 트리거가 되는 수는 **재현 명령과 함께** 적어야 한다 —
숫자가 아니라 **숫자를 만드는 방법**이 산출물이다.

부가로: 정의가 갈릴 수 있는 계수는 "독립표본" 같은 **명사로 부르지 말 것.**
명사는 다섯 개의 결정을 숨긴다.
