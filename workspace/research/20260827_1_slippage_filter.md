## 1. 두 현상을 분리한다

섞으면 진단이 틀린다. 로그 한 줄에서 두 개의 다른 값이 나온다:

```
09:55:16  *** KERNEL/KRW 돌파! 가격: 57  상단: 57 ***     <- 이격 = 57/57 - 1 = 0%
09:55:16  매수 체결: 67.8                                 <- 슬리피지 = 67.8/57 - 1 = +18.9%
```

| 지표 | 정의 | 의미 | 원인 |
| --- | --- | --- | --- |
| **집행 슬리피지** | 체결가 / 신호가 - 1 | 주문이 호가창에 닿는 사이의 이동 | 주문 지연 + 얇은 호가 |
| **밴드 이격** | 신호가 / DC상단 - 1 | 감지 시점에 이미 밴드를 얼마나 넘었나 | 틱 평가 주기 + 종목 자체의 급등 |

KERNEL 은 **이격 0% + 슬리피지 +18.9%**(밴드에서 정확히 감지했으나 집행 중 급등),
SPK 는 **이격 +14.3% + 슬리피지 +0.8%**(감지 시 이미 급등 상태, 집행은 매끄러움).
원인이 다르므로 대책도 다르다.

## 2. 라이브 실측 (§2-A 성공기준)

도구: `scripts/slippage_audit.py` (journalctl 돌파 로그 x state 체결가)

### 2-1. 정밀도 처리

로그 포맷이 `{price:,.0f}` 라 신호가가 정수로 뭉개진다. 체결가는 로그 대신 state 의
`entry_price`(lessons #43 정산 완료, 전정밀도)를 써서 오차원을 하나로 줄이고, 남은
불확실도 `±0.5/신호가` 가 1% 이하인 표본만 집계했다.

- 돌파 신호 21건 → 체결 매칭 20건 → **정밀도 충족 17건**
- 제외: BLAST(로그가 `0` 으로 반올림), VTHO(±50%), VET(±5.6%), SPK(±2.1%)

> ⚠ **journald 타임스탬프는 이벤트 시각이 아니다.** 실측 지연 KERNEL 2.4초 / KITE 61초 /
> **POL 38분**. 분 단위 정확 일치로 매칭하면 21건 중 8건이 통째로 날아간다.
> 권위 시각은 앱이 기록한 `entry_date`. 매칭 윈도우를 ±60분으로 두고 최근접을 택했다.

### 2-2. 분포 (n=17)

| 지표 | 중앙값 | 평균 | 최대 | 1% 초과 |
| --- | ---: | ---: | ---: | ---: |
| 집행 슬리피지 | **+0.12%** | +1.38% | **+18.95%** | 3/17 |
| 밴드 이격 | +1.59% | +3.58% | +11.11% | 10/17 |

**집행 슬리피지 평균의 80%는 KERNEL 한 건이 만든다** — 그 건을 빼면 평균 +0.28%.
즉 평균으로 정책을 세우면 안 되는 분포다. 상시 비용이 아니라 **꼬리 사건**이다.

반대로 밴드 이격은 상시적(10/17이 1% 초과)이며, 이건 정상 동작이다 — 봇이 밴드
돌파 순간의 틱을 잡는 게 아니라 그 이후 첫 평가 틱을 잡기 때문이다.

### 2-3. 이격이 성과를 예측하는가 → **아니다**

필터 도입의 전제는 "이격이 큰 진입이 실제로 나쁘다"이다. 청산 완료 12건:

| 구간 | n | 승률 | 평균 |
| --- | ---: | ---: | ---: |
| 이격 ≤ 3% | 7 | 43% | -1.26% |
| 이격 > 3% | 5 | 40% | -2.67% |

방향은 "이격 큰 쪽이 나쁨"이나 **n=5 대 7 로 판정 불가**이고 차이도 노이즈 범위다.
개별로 봐도 일관성이 없다 — 이격 +14.3%(SPK)는 +8.77% 승, 이격 +11.1%(XRP)는 -10.04% 패,
이격 +0.1%(INJ)도 -10.32% 패.

## 3. 슬리피지 비용 민감도 (§2-B 성공기준)

`backtest_param_sweep.py --axis slip` / 61종목 / 700일 / 무작위선택 20회 평균
(IS 거래가능 220일 / OOS 146일)

| 슬리피지 | IS 평균 | OOS 평균 | OOS MDD | 거래 | 승률 | **건당평균** |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 0% (백테스트 가정) | -7.0% | **+14.1%** | -15.5% | 153 | 61.6% | **+1.25%** |
| 0.5% | -14.9% | +9.2% | -16.4% | 151 | 59.7% | +0.84% |
| 1.0% | -18.1% | +5.0% | -18.8% | 150 | 57.9% | +0.42% |
| 2.0% | -23.4% | **-2.8%** | -19.5% | 146 | 54.0% | -0.27% |
| 5.0% | -47.8% | -27.0% | -29.7% | 146 | 39.4% | -2.88% |

### 3-1. 기울기는 선형, 소멸점은 약 1.6%

슬리피지 1%p 당 건당수익 **-0.83%p** (0→0.5 구간 -0.82, 0.5→1.0 구간 -0.83).
외삽하면 건당수익 0 이 되는 지점은 **슬리피지 ≈ 1.6%**, OOS 수익이 0 이 되는
지점도 ≈ 1.64% 로 거의 같다.

### 3-2. 왜 1% 가 1%p 가 아니라 0.83%p 인가

진입가가 부풀면 TP 트리거(`진입가 x 1.055`)와 하드손절(`x 0.9`)이 **함께 위로
밀린다**. 모두 비례하면 수익률은 불변이어야 하나, **시장은 밀리지 않는다** — TP 에
닿으려면 시세가 그만큼 더 올라야 한다. 1:1 보다 덜 깎이는 건 트레일링스톱이
**ATR(절대값)** 기준이라 비례 확대되지 않기 때문.

→ 슬리피지는 "수수료처럼 한 번 떼이는 비용"이 아니라 **익절 문턱을 올리는** 방식으로
작동한다. 승률이 61.6% → 57.9%(1%) → 54.0%(2%) 로 떨어지는 게 그 증거다.

### 3-3. 라이브 분포를 대입하면

| | 슬리피지 | 건당 비용 |
| --- | ---: | ---: |
| 전형적 거래 (중앙값) | 0.12% | **-0.10%p** — 무시 가능 |
| 꼬리 사건 (17건 중 1건) | 18.9% | 손절선이 시세 아래 → 즉시 청산 영역 |

꼬리 1건의 실현 손실은 -1.28% 였으나 그건 급등이 이어졌기 때문이고,
시세가 58 에 머물렀다면 **-14%** 였다(체결 67.8 vs 시세 58).
17건에 걸쳐 분산하면 **-0.8%p** — 백테스트 엣지(+1.25%p)의 **3분의 2**.

> **그래서 대책은 필터가 아니다.** 전형적 거래의 슬리피지는 이미 무해하므로 진입
> 후보를 걸러도 얻을 게 없고, 꼬리는 진입 *전*에 식별되지 않는다
> (KERNEL 의 이격은 **0%** 였다). 유효한 지점은 **체결 직후** 뿐이다.

## 4. 이격 필터는 일봉 백테스트로 측정 불가 (§2-C, §2-D 성공기준)

**시도했고, 실패했으며, 그 실패가 결과다.**

`backtest_param_sweep.py` 의 진입가는 `entry_px = max(DC상단, 시가)` 다. 따라서
일봉에서의 이격 `entry_px/upper - 1` 은 **시가가 이미 밴드 위일 때(갭상승)만** 0보다 크다.

실측 (40종목 / 700일 / 1,733 돌파신호):

| | 값 |
| --- | --- |
| 이격 > 0 인 신호 | **2건 (0.1%)** |
| 이격 최대 | **+0.041%** |
| 이격 > 1% | 0건 |

**원인**: 암호화폐는 24시간 연속 거래라 일봉의 `open ≈ 전일 close` — 주식과 달리
갭이 존재하지 않는다. 주식 백테스트에서 빌려온 갭 개념이 이 시장에서는 죽은 변수다.

**`high` 기준으로 바꾸면?** 변별력은 생기지만(KERNEL 당일 저 51.1 → 고 69.8 = +37%)
진입 시점에 당일 고가를 알 수 없으므로 **lookahead bias** 다. 필터로 쓸 수 없다.

→ 이 현상은 **일봉 아래에 살고 있다.** 일봉 백테스트로는 원리적으로 평가할 수 없으며,
이 사실을 결과로 명시한다(계획 §2-D). 축은 제거하고 음성 결과를 코드 주석으로 남겼다
(`build_panel` 내부 — 재시도 방지).

## 5. 결정적 발견 — 이건 슬리피지가 아니라 **신호 지연**이다

분봉으로 KERNEL 을 재구성하자 진단이 바뀌었다.

```
09:50 UTC  밴드(57.2) 최초 돌파 — 분봉 O 56  H 57.8 L 55.9 C 57    (+1.0%)
09:51                                O 57  H 59.8 L 56.6 C 59.6  (+4.5%)
09:52                                O 59.5 H 64.9 L 59.2 C 64.8 (+13.5%)
09:53                                O 64.8 H 69.8 L 64.3 C 67.1 (+22.0%)  <- 당일 정점
09:55  봇이 67.8 에 매수       O 65.4 H 67.8 L 65   C 66.8 (+18.5%)
```

**09:55 분봉에는 57원 거래가 없다.** 그런데 로그의 신호가는 57 이고
ML shadow 의 `signal_ts` 는 09:55:14 다. 즉 봇은 **5분 된 가격으로 판단했고**,
주문은 현재가(67.8)에 정상 체결됐다.

### 5-1. 전체 매수 검증 (08-27 6건)

신호가가 **신호 시각의 분봉 범위 안에 있는가**:

| 종목 | 신호시각 | 신호가 | 그 분봉 L~H | 포함 | 체결가 | 포함 |
| --- | --- | ---: | --- | :-: | ---: | :-: |
| VET | 00:03:03 | 9 | 9.3~9.36 | (반올림) | 9.36 | ✓ |
| SPX | 00:45:14 | 855 | 862~865 | **✗** | 865 | ✓ |
| KITE | 01:28:14 | 167 | 166~167 | ✓ | 167 | ✓ |
| KITE | 06:42:29 | 183 | 181~184 | ✓ | 183 | ✓ |
| FF | 08:47:07 | 146 | 143~145 | (반올림) | 145 | ✓ |
| KERNEL | 09:55:14 | 57 | 65~67.8 | **✗** | 67.8 | ✓ |

**체결가는 6/6 모두 당시 분봉 안에 있다** — 주문 집행은 정상이다.
어긋나는 건 신호가뿐이고, 지연은 **가변적**이다(KITE 0분 / SPX ~1분 / KERNEL ~5분).

### 5-2. 메커니즘 — 가설 (미확정)

이벤트 루프는 멈추지 않았다(09:50~09:55 내내 틱 처리 로그 연속).
그런데 `_execute_buy` 는 `async def` 안에서 **동기 블로킹 `get_balance()` 를
직접 호출**한다(realtime_monitor.py:2183, 2371). 이 함수는 `_retry_on_429` 로
**1s/4s/16s 백오프**를 갖는다(upbit_client.py:167~182) — 호출당 최악 ~21초 동안
루프 전체가 멈춘다.

가설: 이 짧은 정지가 반복되면 **웹소켓 메시지가 백로그로 쌓이고**, 루프가
재개될 때 오래된 틱부터 처리한다. 루프는 "살아있지만 과거를 보고 있는" 상태가 된다.
거래량 필터 로그는 throttle 되어 있어(lessons #14) 백로그를 드러내지 않는다.

> ⚠ **이건 가설이지 입증이 아니다.** 확인하려면 계산이 아니라 **계측**이 필요하다 —
> 업비트 웹소켓 ticker 메시지는 자체 `timestamp` 를 실어 보낸다. 그걸
> 수신 시각과 비교해 **틱 지연(tick lag)** 을 기록하면 끝난다.

### 5-3. 그래서 손절선이 무너졌다

진단이 바뀌어도 손절선 문제는 그대로다:

KERNEL 에서 손실을 만든 건 "나쁜 종목을 샀다"가 아니다:

```
신호가 57  →  체결가 67.8  →  하드손절선 = 67.8 x 0.9 = 61.0
                                신호가 기준이었다면 = 57 x 0.9 = 51.3
```

체결가가 부풀면 **손절선도 함께 부푼다**. 실제 시세가 58 로 돌아오자 61.0 을 밑돌아
즉시 손절됐다 — 즉 **진입하는 순간 이미 손절 영역에 있었다**.

이건 진입 후보 선택(필터)의 문제가 아니라 **회계 기준점**의 문제이며,
대응 후보는 필터가 아니다:

| 후보 | 내용 | 평가 |
| --- | --- | --- |
| **(0) 틱 지연 계측** | ticker 메시지 `timestamp` vs 수신시각 기록 | **먼저.** 원인 확정 전에는 나머지를 고를 수 없다 |
| (a) 체결 후 괴리 검사 | `체결가/신호가 - 1 > X` 면 즉시 청산 | 증상 완화. 원인을 남긴 채 손실만 막는다 |
| (b) 지연 신호 폐기 | 틱 지연 > N초면 신호 무시 | (0)이 선행되어야 임계 N 을 정할 수 있다 |
| (c) 블로킹 호출 제거 | `get_balance()` 를 executor 로 / 잔고 캐시 | 가설이 맞다면 **근본 처방** |
| (d) 지정가 주문 | 시장가 → 지정가 상한 | 체결 실패 리스크, 추세추종과 상충 |

✗ **기각: 진입 필터 전반** — 전형적 거래의 슬리피지는 이미 0(§4-1)이고,
KERNEL 은 진입 시점 이격이 **0%** 였다. 걸러낼 신호 특징이 없다.

**이 문서는 채택을 결정하지 않는다** — 측정만 산출한다(계획 §1).
다만 **(0)은 계측 항목이지 전략 변경이 아니므로** 별도 ADR 없이 진행 가능하다.

## 6. 부수 적발: 백테스트 표본의 조용한 축소

측정 도중 `backtest_param_sweep.py` 가 **120종목 중 16종목만 로드한 채 멀쩡한 결과표를
출력**하는 것을 발견했다. 원인은 다른 프로세스(이 측정의 분봉 스크립트)가 DuckDB 캐시를
잠근 사이 로딩 예외가 `except Exception: continue` 로 조용히 삼켜진 것.

출력에서 달라지는 건 `종목 16` 한 줄뿐이라 알아채기 어렵다.
**조용한 축소는 조용한 실패보다 위험하다 — 결과가 나오기 때문이다.**

수정:
- 로딩 예외 건수/종류를 경고로 출력
- 로드 종목이 최소치 미만이면 `[중단]` 후 `return 1` (역방향 테스트 1/1 통과)
- 분봉 스크립트는 캐시를 아예 쓰지 않도록 ccxt 직결로 전환(일회성 조사 데이터는
  영속 캐시에 넣을 성격이 아니다)
