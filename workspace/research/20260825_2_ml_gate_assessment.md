# ML 게이트 운영 의미 재평가 (2026-08-25)

- **발단**: 사용자 질문 — "ml 게이트 운영 의미 현 시점에서 분석해봐"
- **왜 지금인가**: 오늘 슬롯을 5 → 15로 늘렸다(ADR 20260825-1). 슬롯은 *용량*이고
  ML 게이트는 *용량을 깎는 장치*다. 둘의 방향이 정면으로 부딪히므로 재평가가 필요하다.
- **결론 요약**: (1) 게이트는 2026-05-16부터 **꺼져 있다**, (2) 꺼진 줄 알았던 shadow
  수집도 **같이 죽어 있다**(설계 결함), (3) 켤지 말지를 판단할 **독립 표본이 3건**이다.

---

## 1. 현재 실제 상태 — 문서와 다르다

| | CLAUDE.md 기술 | 서버 실제 |
|---|---|---|
| 게이트 | "ML 게이트(threshold 0.45)" 적용 중 | `ML_FILTER_ENABLED=0` → **비활성** |
| 임계값 | 0.45 | `ML_FILTER_THRESHOLD=0.40` (쓰이지도 않음) |
| 모드 | LIVE (ADR 20260505-2 "LIVE 가속") | shadow 표기이나 **점수 자체를 안 냄** |

근거는 systemd 드롭인이다:

```ini
# /etc/systemd/system/btc-trader.service.d/ml.conf
# ML SHADOW 전환 (ADR 20260515-1 Phase A NO-GO 명중)
# 사유: 5/9~5/16 평가 PF=0.23, Accuracy=42.1%, FN=11 — 모델 과보수
#       차단률 100%, 통과 매수 4건 1승3패. 필터가 비용.
Environment="ML_FILTER_ENABLED=0"
Environment="ML_SHADOW_MODE=1"
```

**3개월 넘게 문서와 운영이 갈라져 있었다.** 최근 shadow 로그가 이를 그대로 보여준다:

```json
{"symbol":"EGLD/KRW","score":1.0,"threshold":0.4,"will_buy":true,"ml_active":false}
```

`score: 1.0`은 모델 출력이 아니라 **비활성 시 채워 넣는 자리표시자**다(`_ml_score = 1.0` 초기값).
08-22~08-24 기록 18건 전부 이 형태 — 즉 최근 매수 5건은 ML 판단을 받은 적이 없다.

## 2. ⚠ 정정 (2026-08-25 당일) — "설계 결함" 진단은 틀렸다

초고에서 **"차단 없이 점수만 모으는 상태가 코드상 존재하지 않는다"** 고 썼으나 오진단이다.
호출부의 else 분기만 읽고 `MLFilter.passes()` 내부를 확인하지 않았다.

```python
def passes(self, score: float) -> bool:
    if not self.is_active:
        return True
    if os.getenv("ML_SHADOW_MODE", "1") == "1":
        return True          # ← shadow 를 이미 처리하고 있었다
    return score >= self.threshold
```

서버 실측(`ML_FILTER_ENABLED=1 ML_SHADOW_MODE=1`):

```
is_active: True | threshold: 0.4
score(BTC): 0.1045          ← 임계 미만
passes(score): True         ← 차단 안 함
SHADOW=0 일 때 passes(0.01): False   ← LIVE 차단 정상
```

### 그럼 증상의 진짜 원인은

`ML_FILTER_ENABLED=0` 이 **모델 로드 자체를 막기 때문**이다.
`_load_if_possible()` 이 `disabled (ML_FILTER_ENABLED!=1)` 로 조기 반환 → `is_active=False`
→ 점수를 산출하지 않고 자리표시자 1.0 이 기록된다.
즉 **정책(수집 유지)과 설정(ENABLED=0)이 어깋난 것**이지 구조적 불가능이 아니었다.

### 실제로 있었던 결함 (좁음)

호출부의 `_ml_pass = passes(score) and not _ml_exception` —
**추론 예외가 shadow 를 덮어썼다.** 점수만 모으려고 켜둔 상태에서
오류 1번이 매수를 막으면 그건 관측이 아니라 동작 변경이다. 수정했다(§6).

## 3. 판단 근거의 실체 — 표본 3건

shadow 로그를 액면대로 세면 강력해 보인다:

| 집계 방식 | 표본 | 실측 AUC | 상위 25% 도달률 |
|---|---:|---:|---:|
| 원본 행 그대로 | 1,555 | **0.781** | 33.2% (기저 14.1% 대비 2.4x) |
| **(종목, 일) 중복 제거** | **3** | 판정 불가 | 판정 불가 |

**차이의 원인은 pseudo-replication이다.** 봇은 돌파 감지마다 점수를 기록하는데,
같은 종목이 하루에 수백 번 재평가된다:

| 날짜 | 채점 건수 | 고유 종목 | 종목당 재평가 |
|---|---:|---:|---:|
| 2026-05-10 | 1,070 | 61 | 17.5회 |
| 2026-05-13 | 21 | 1 | 21.0회 |
| **2026-05-14** | **1,711** | **2** | **855.5회** |

outcome 매칭도 같은 배율로 복제된다(1,565 outcome 행 → 고유 (종목,일) **17개**).
점수와 결과가 **동시에** 있는 독립 조합은 **3건**이다. 95% 신뢰구간이 ±53%p다.

> 즉 "AUC 0.78"은 모델의 성능이 아니라 **한 종목을 855번 센 결과**다.
> ADR 20260824-2가 정리한 원칙("표본 수를 먼저 계산한다")이 여기에도 그대로 적용된다.

부수적으로, 게이트를 껐던 근거(ADR 20260515-1)도 **통과 매수 4건**에 기반한다.
방향은 옳았다 — 차단률 100%는 표본과 무관하게 그 자체로 고장이다 — 그러나
"필터가 비용"이라는 결론의 강도는 n=4였다.

## 4. 임계값이 안 맞는 이유 — 모델이 보수적인 게 아니라 prior가 다르다

라이브 점수 분포(중복 포함 2,812건, 상대 비교용):

```
min 0.034 / p25 0.114 / median 0.147 / p75 0.214 / max 0.42
```

| 임계 | 통과율 | 차단률 |
|---|---:|---:|
| 0.35 | 2.31% | 97.7% |
| **0.40 (현재 설정값)** | **0.71%** | **99.3%** |
| 0.45 (CLAUDE.md 기술값) | 0.36% | 99.6% |
| 0.55 (모델 메타 기본값) | 0.36% | 99.6% |

원인은 **학습/운영 prior shift**다. 모델 메타를 보면 학습 표본의
`positive_rate = 0.486`인데, 라이브에서 "+5% 도달"은 14% 수준이다.
XGBoost 확률 출력은 학습 분포에 맞춰 교정되므로, 라이브에서는 점수가 통째로
낮은 구간에 몰린다. 여기에 0.4~0.55라는 **절대 임계**를 걸면 전량 차단이 된다.

→ 임계는 확률의 절대값이 아니라 **당일 후보 분포의 백분위**로 정의해야 한다.

모델 자체의 교차검증 성적도 기억해 둘 것: `mean_auc = 0.553`
(폴드별 0.505~0.587). 동전 던지기보다 아주 조금 나은 수준이다.

## 5. 슬롯 확대가 게이트의 경제성을 바꿨다

오늘 측정(ADR 20260825-1)에서 슬롯을 늘릴수록 거래 수가 계속 늘었다:

| 슬롯 | 5 | 10 | 15 | 20 |
|---|---:|---:|---:|---:|
| OOS 거래 수 | 65 | 113 | 134 | 148 |

**20슬롯에서도 아직 포화되지 않았다 = 신호가 용량보다 많다.** 이건 두 가지를 동시에 뜻한다.

1. **게이트를 "신호를 줄이는 장치"로 쓰면 슬롯 확대를 되돌린다.**
   상위 25%만 취하면 거래 수가 1/4로 줄어 슬롯 5 시절보다 못한 거래 빈도가 된다.
2. **그러나 용량이 제약이라는 건 "무엇을 고르느냐"에 가치가 있다는 뜻이기도 하다.**
   ADR 20260823-2가 남긴 미해결 항목 — "진입 후보 선택 규칙" — 이 정확히 이 자리다.
   현재 봇은 **먼저 돌파한 순서대로**(FCFS) 슬롯을 채운다. 무작위 선택이 결과를
   14%p 좌우한다는 측정이 있었으니, 순서를 점수로 바꾸는 것은 원리적으로 유효하다.

→ 결론: 게이트의 올바른 역할은 **차단(filter)이 아니라 정렬(ranker)** 이다.
빈 슬롯이 남아 있으면 점수가 낮아도 담고, 후보가 슬롯보다 많을 때만 점수로 고른다.
지금 코드에는 이 구분이 없다(절대 임계 통과/차단 이분법).

## 6. 조치 (2026-08-25 실행 완료)

**수집만 재개했고 LIVE 로는 전환하지 않았다.** 켜면 99% 차단되어
오늘의 슬롯 확대(ADR 20260825-1)가 무의미해진다.

| 조치 | 내용 |
|---|---|
| systemd drop-in | `ML_FILTER_ENABLED=0 → 1` (SHADOW_MODE=1 유지) — 점수 산출 재개, 차단 없음 |
| `MLFilter.shadow` | 프로퍼티 신설 — 호출 시점에 환경변수 재평가(싱글톤 고정 방지) |
| `MLFilter.would_block()` | LIVE였으면 차단했을지를 로그에 기록 — shadow 중 `will_buy`는 항상 True라 이 값이 없으면 평가 불가 |
| 호출부 2곳 | `passes(score) and (shadow or not exception)` — shadow 중 추론 예외가 차단으로 번지지 않는다 |
| `shadow.log_decision` | **(종목, 종류, UTC날짜) 중복 억제** — 855배 복제 차단. 억제 건수는 `suppressed_counts()` |
| 검증 룰 | `check_ml_shadow_integrity()` — shadow/would_block 정의 + 판정식 우선순위 + 중복 억제 (역방향 4/4) |

### 게이트 판정 진리표 (서버 실측)

| | 저점수 정상 | 저점수+추론예외 | 고점수 |
|---|---|---|---|
| SHADOW=1 (현재) | 매수 O | **매수 O** | 매수 O |
| SHADOW=0 (LIVE) | 매수 X | 매수 X | 매수 O |

### 다음 판정까지

기저 도달률 14%에서 상위 25%가 25%로 오르는지(1.8x)를 95% 신뢰수준·80% 검정력으로
확인하려면 상위군 약 200건 → **총 800 신호**가 필요하다.
중복 억제 후에는 "신호 1건 = 기록 1건"이므로 로그 행 수를 그대로 세면 된다.

> 이 수치를 먼저 적어두는 이유: ADR 20260515-1은 **n=4**로 꺼고,
> 그 전 ADR 20260505-2는 더 적은 근거로 켰다. 다음엔 표본 수를 먼저 본다.

## 7. 부수 발견 — 게이트가 이미 지불한 비용

2026-05-05 ~ 05-16 사이 게이트가 LIVE였던 기간의 차단률은 100%였다.
그 기간 매수는 4건뿐이었고, 그중 3건이 손실이었다. 슬롯이 놀았다는 뜻이다.
지금 관점에서 보면 **"필터가 비용"이라는 표현은 정확했지만 이유가 달랐다** —
모델이 나빠서가 아니라 **임계가 분포와 어긋나서** 전량 차단된 것이다.
같은 실수를 반복하지 않으려면 임계를 절대값으로 두지 않아야 한다(4절).
