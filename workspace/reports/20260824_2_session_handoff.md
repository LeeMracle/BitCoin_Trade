## 2. 이번 세션 처리분

### (a) 유령 포지션 버그 수정 — lessons #45

**원인**: 잔고 0 자동정리(lessons #28)가 TP 루프 **안**에 있어서, 모든 TP 단계가
매도되면 루프가 전부 `continue`로 빠져나가 종료 코드가 **구조적으로 도달 불가능**.
`_check_tp_levels`는 "부분매도" 함수인데 "생애주기 종료"까지 얹혀 있던 관심사 혼재.

**동반 적발 3건**:
1. `_execute_sell`의 잔고 0 경로가 `closed_trades` 없이 `del` — 표본 소실 두 번째 경로
2. `return_pct`가 마지막 체결가만 반영 → **부분 익절 이익이 통계에서 소실**
   (+5%에 절반 실현 후 +1% 이탈 → `+1%` 기록, 실제 +3%). `multi_trader`에도 동일 산식
3. TP 직후 `remaining_qty`가 업비트 정산 전 값(매도 전 수량)으로 기록

**수정**: `services/execution/position_pnl.py` 신설(매도 경로 3개가 손익 산식 공유,
순환 import 회피) + `_close_position()` 단일 종료 경로 + 루프 **앞** 안전망 +
루프 **안** 근본 경로 + `config.FEE_RATE`/`POSITION_DUST_KRW` 등재 +
`scripts/backfill_realized_pl.py`(journal 실측 체결로 기존 4포지션 보정).

**실측 효과**: 보유 5→4(슬롯 회수) → STX 신규 진입. 표본 0→1건.

### (b) TP1 +5% → +5.5% — ADR 20260824-1

사용자 결정. 수수료 0.05%×2를 덮고 순 +5%를 남긴다. **부분 익절 50% 유지**(전량 아님).

측정상 개선 근거는 **없다**(아래 §3). 사용자에게 데이터와 대안 3종을 제시한 뒤
원안을 선택받아 반영했다. 성과 최적화가 아니라 "익절선을 실수령 기준으로 정렬"한 결정.

기준선을 2026-08-24로 재리셋(비용 1건, `closed_trades` 27건 보존).

## 3. ⚠ 다음 세션이 알아야 할 것 — TP 측정 결과

`scripts/backtest_param_sweep.py --axis tp55 --runs 20` (49종목/700일, IS·OOS 분리):

| 설정 | IS | OOS | OOS 표준편차 | 승률 |
|---|---:|---:|---:|---:|
| 기존 5%/50%+12% | -18.9% | +0.5% | 5.1% | 53.6% |
| **현행 5.5%/50%+12%** | **-20.0%** | **+2.3%** | 5.3% | 55.6% |
| 5.5% 전량 | -27.5% | +2.2% | 4.0% | 66.1% |
| 5.0% 전량 | -23.9% | -1.5% | 4.6% | 66.7% |
| **15% 전량** | **-13.3%** | **+17.0%** | 6.6% | 48.6% |

세 가지를 기억할 것:

1. **5.5%와 기존 5%는 통계적으로 구분되지 않는다.** 차이 1.8%p, 표준오차 ≈1.2%p.
   IS에서는 방향이 반대. 즉 현행 설정은 "개선된 것"이 아니라 "중립인 것"이다.
2. **TP1을 늦출수록 크게 개선된다.** 08-23 탐색에서도 독립적으로 같은 방향이 나왔다
   (슬롯15+TP15% = IS +3.3% / OOS +15.2%, 26개 설정 중 IS·OOS 동시 양수 2개 중 하나).
3. **어느 설정도 IS 양수가 아니다.** TP 조정만으로 ADR 20260823-2의 포트폴리오
   수익성 문제는 해결되지 않는다. 승률이 높을수록 수익이 낮은 비대칭이 핵심
   (66.7%/-1.5% vs 48.6%/+17.0%) — 손실은 -10%까지 가는데 이익은 +5.5%에서 잘린다.

### 레짐 구간 커버리지 (교훈 #2 — 상승장 편향 점검)

이 측정은 **레짐 게이트(BTC > EMA200)가 켜진 상태로** 시뮬레이션했으므로, 표본은
정의상 상승장 구간에 몰린다. 별도 하락장 표를 만들 수 없는 것이 아니라
**전략이 하락장에서는 진입 자체를 하지 않기 때문**이다.

| 구간 | 전체 일수 | 거래가능(BULL) 일수 | 통과율 |
|---|---:|---:|---:|
| IS (~2025-06-15) | 266 | 222 | 83.5% |
| OOS (2025-06-16~) | 434 | 147 | 33.9% |

IS/OOS를 **달력이 아니라 거래가능일 60% 지점**으로 나눈 이유가 여기 있다.
달력 60/40으로 자르면 OOS가 통째로 레짐 폐쇄 구간(2026 Q1/Q2 통과율 **0%**)에
들어가 거래 3~16건뿐인 무의미한 표본이 된다.

따라서 위 수치는 "상승장 성과"로 읽어야 하며, 하락장 방어는 TP가 아니라
**레짐 필터 + 하드 손절 -10% + 서킷브레이커**가 담당한다.
OOS의 BULL 통과율이 33.9%로 IS(83.5%)보다 크게 낮다는 점도 감안할 것 —
OOS 쪽이 더 척박한 환경이었는데도 15% 설정이 +17.0%를 낸 것이다.

ML 모델 재학습 시 함께 정렬한다. ADR 20260824-1 §3에 문서화됨.

## 6. 이 프로젝트에서 반복되는 함정 (유지)

### 검증 룰이 자기 주석에 속는다 — 이번 세션에도 재확인

`pre_deploy_check.py`의 문자열 포함 검사가 코드와 주석을 구분 못 해 무력화된 사례가
직전 세션에만 3회. 이번에 추가한 `check_position_close_outside_tp_loop()`는
**AST 기반**으로 작성했다(주석·docstring은 AST에 없다).

**역방향 테스트가 실제로 룰의 결함을 잡았다.** 5개 변이 케이스 중 "루프 안 종료 확정
삭제"가 초안에서 통과해버렸다 — 루프 안에 잔고 0 정리용 `_close_position`이 **따로**
있어서 매칭된 것. `sell_market_coin` 이후 lineno 비교로 바꿔 해결.

> **룰을 추가하면 반드시 버그를 재현해 발화하는지 확인할 것.**
> 통과 확인만으로는 룰이 아무것도 안 하고 있을 수 있다.

### 배포 순서 — state 마이그레이션이 있으면 봇을 먼저 멈춰야 한다

봇은 `self.state`를 메모리에 들고 주기적으로 `save_state()` 한다.
가동 중 state 파일을 고치면 곧바로 덮어써진다. 또 새 코드가 먼저 뜨면 안전망이
유령을 자동 정리하는데, 그때는 `realized_pl_krw`가 없어 **현재가 폴백**으로
틀린 수익률이 기록된다.

→ **봇 정지 → 코드 배포 → 마이그레이션 → 봇 기동** 순서.
`hotfix_deploy.sh`는 재시작이 먼저라 이 경우 쓸 수 없다(이번엔 수동 진행,
게이트는 `.env`가 있는 **서버에서** `pre_deploy_check.py` 실행으로 대체).

### t3.micro 메모리 (교훈 #5)

백테스트 sweep이 233MB를 쓴다. 총 911MB에 봇이 상시 가동 중이므로,
sweep 실행 시 `free -m` 감시 필수. 이번엔 가용 221MB로 버텼으나 여유가 크지 않다.
