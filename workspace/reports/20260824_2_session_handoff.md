## 2. 이번 세션 처리분

### (a) 유령 포지션 버그 — lessons #45

잔고 0 자동정리(lessons #28)가 TP 루프 **안**에 있어서, 모든 TP 단계가 매도되면
루프가 전부 `continue`로 빠져나가 종료 코드가 **구조적으로 도달 불가능**했다.
`_check_tp_levels`는 "부분매도" 함수인데 "생애주기 종료"까지 얹혀 있던 관심사 혼재.

**손절은 `_execute_sell`이 정상 제거하므로 이익 청산에서만 발생** — 즉
**잘 된 거래일수록 기록이 안 남는** 하방 편향이었다.

동반 적발 3건:
1. `_execute_sell`의 잔고 0 경로가 `closed_trades` 없이 `del` — 표본 소실 두 번째 경로
2. `return_pct`가 마지막 체결가만 반영 → 부분 익절 이익이 통계에서 소실
3. TP 직후 `remaining_qty`가 업비트 정산 전 값으로 기록

수정: `services/execution/position_pnl.py` 신설(매도 경로 3개가 손익 산식 공유) +
`_close_position()` 단일 종료 경로 + 루프 앞 안전망 + 루프 안 근본 경로.

**실측 검증**: POL이 `tp2_full_exit`로 정상 종료되고 슬롯을 반환해 EGLD 신규 진입.

### (b) 수동 매도 자동 인식

`_close_manually_sold()` 신설. 1시간 주기 교차검증이 `only_state`를 3회 연속 확인하면
**거래소 체결 이력에서 실제 매도가를 읽어** 정확한 손익으로 청산한다.
재구성 실패 시 청산하지 않고 알림만 보낸다(fail-closed).

`fix_state_balance_mismatch.py`도 제거 시 `closed_trades`를 기록하도록 수정
— 표본 소실 **세 번째 경로**였다.

### (c) 손익 정합화 — journal 기반 backfill이 틀렸다

`rebuild_realized_from_exchange()`를 만들어 검증하다가 발견:

journal의 `pl` 값 자체가 신호가 기준이었다. 내 backfill이 그 오염을 물려받았다.

### (d) TP 파라미터 2건 (ADR)

## 3. ⚠ 다음 세션이 반드시 알아야 할 것

### (1) 실거래 30건은 "실행 검증"용이지 파라미터 선택용이 아니다

건당 평균 0.52% / 건당 편차 8.57% 기준:

    n=30 → 표준오차 1.57%p → 95% CI [-2.55%, +3.59%]   ← 0을 포함

| 알고 싶은 것 | 필요 표본 |
|---|---:|
| "수익이 나는가" | 약 **1,064건** |
| "TP 10% vs 15% 중 뭐가 나은가" | 약 **9,700건** |

레짐 개방률을 감안하면 수십 년이다. **ADR 20260823-1의 30건은
체결가·필터·버그가 설계대로 도는가를 보는 것이고, 파라미터 선택은 백테스트로만 가능하다.**
두 질문을 섞지 말 것.

### (2) TP 측정 결과 — 15% 부근에 봉우리

TP1 축(`--axis tp55`)과 TP2 축(`--axis tp2`)이 **독립적으로 15%를 가리킨다.**

TP2 단독 측정 (TP1 5.5% 고정, 45종목/700일):

| TP2 | IS | OOS | 승률 | 건당 |
|---|---:|---:|---:|---:|
| 8% | -14.1% | +3.4% | 62.5% | 0.37% |
| **10% (현행)** | -11.9% | +7.0% | 60.2% | 0.60% |
| 12% (구) | -11.2% | +6.0% | 58.2% | 0.52% |
| **15%** | **-5.3%** | **+8.0%** | 57.1% | **0.77%** |
| 20% | **-0.2%** | +4.6% | 54.9% | 0.45% |
| 30% | +1.8% | **-1.3%** | 53.7% | -0.28% |

- **30%에서 뒤집힌다** (IS 유일 양수인데 OOS 음수 = 과최적화). "늦출수록 좋다"가 아니다
- **어느 설정도 IS 양수가 아니다** — TP 조정만으로 ADR 20260823-2는 해결 안 됨
- 다음 변경은 TP 단독이 아니라 **슬롯 수와 결합** (08-23 탐색에서 IS·OOS 동시 양수는
  슬롯15+TP15%뿐)

### (3) 건드리지 말 것 — `LABEL_TARGET_PCT`

`services/ml/config.py:29` `LABEL_TARGET_PCT = 0.05`는 ML 게이트가 학습한
"+5% 도달" 라벨 기준이다. TP와 어긋나지만 **재학습 없이 상수만 바꾸면
threshold 0.45 보정이 깨진다.** ML 재학습 시 함께 정렬.

   훨씬 경미하고 방향도 보수적(손절선이 약 1.3% 더 타이트). 거래량 필터는 `iloc[-2]`로
   고쳐졌는데 ATR은 안 됨. Donchian은 `.shift(1)`이 있어 문제없음.
   실측 POL: ATR 7.81(현행) vs 8.42(완성봉) → 손절선 138.57 vs 136.75.
   고치면 손절 거리가 바뀌어 표본에 영향 → **30건 이후 검토**
3. 디스크 86% (약 960MB 여유)
4. dust 3종(PYTH/SOLO/XCORE) — `state↔balance` 경고 상시 발생
5. VB 비활성인데 보고서에 43건 통계 노출 (노이즈)
6. TAIKO `entry_qty` 미세 불일치 — 실매도 237.61 vs 계산상 235.43.
   손익 영향 없음(거래소 이력 기준 재구성으로 흡수)

## 5. 반복되는 함정

### 검증 룰은 "실패를 잡는지"로 검증한다

문자열 포함 검사가 자기 주석에 속은 사례가 직전 세션에만 3회.
이번에 추가한 `check_position_close_outside_tp_loop()`는 **AST 기반**이다
(주석·docstring은 AST에 없다).

**역방향 테스트가 실제로 룰의 결함을 잡았다** — 5개 변이 케이스 중 "루프 안 종료 확정
삭제"가 초안에서 통과했다(루프 안에 잔고 0 정리용 종료 호출이 따로 있어 매칭됨).
`sell_market_coin` 이후 lineno 비교로 수정.

### 배포 순서 — state 마이그레이션이 있으면 봇을 먼저 멈춘다

봇은 `self.state`를 메모리에 들고 주기적으로 `save_state()` 한다.
가동 중 state 파일을 고치면 덮어써진다. 또 새 코드가 먼저 뜨면 안전망이 유령을
자동 정리하는데, 그때 `realized_pl_krw`가 없으면 현재가 폴백으로 틀린 값이 남는다.

→ **봇 정지 → 코드 배포 → 마이그레이션 → 봇 기동.**
`hotfix_deploy.sh`는 재시작이 먼저라 이 경우 쓸 수 없다.
게이트는 `.env`가 있는 **서버에서** `pre_deploy_check.py` 실행으로 대체한다.

### 로그·문서의 숫자를 진실로 믿지 말 것

journal의 `pl=+1662`가 실제로는 +1,511이었다(신호가 기준). **거래소 `fetch_order(uuid)`가
유일한 진실 원천**이다. `fetch_closed_orders` 목록만으론 안 된다 — 매도 항목의
`average`/`price`/`cost`가 전부 None이다(lessons #43).

### t3.micro 메모리 (교훈 #5)

백테스트 sweep이 233MB를 쓴다. 총 911MB에 봇이 상시 가동 중이므로
sweep 실행 시 `free -m` 감시 필수.
